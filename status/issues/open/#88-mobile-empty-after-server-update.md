# #88 — Мобильный клиент: после обновления сервера интерфейс «пустеет»

## Симптом
После обновления сервера мобильное приложение заходит нормально (чаты
видны), затем всё исчезает: оболочка интерфейса остаётся, но списка чатов
нет, профиль не отображается (плейсхолдеры). Перезапуск приложения лечит.

## Анализ кода (кандидаты, web_client)

1. **Загрузочный REST без повторов** — `HomeScreen` грузит список и профиль
   один раз при монтировании: `getChats().catch(() => undefined)` и
   `getMe().catch(() => undefined)`. Если вход совпал с окном рестарта
   сервера (после обновления это типично), вызовы молча падают: chats=[],
   username=null («...» в настройках = «нет профиля»). WS сам
   переподключается, но getChats/getMe больше никто не перезапускает.
   Перезапуск приложения повторяет boot → «лечит». Главный подозреваемый.

2. **Нет обработки 401** — REST-обёртка не различает 401: если обновление
   сбросило сессии (чистая БД/секрет), клиент становится «зомби»: оболочка
   рисуется, все запросы молча падают. Тот же визуальный симптом
   (но перезапуск сам по себе не чинит — нужен ре-логин).

3. **Возврат из фона на Android только переконнектит WS**
   (`app-foreground` -> `ws.reconnect()`), REST-состояние не освежается:
   после убийства/восстановления процесса список зависит целиком от реплея
   от сохранённого lastSeq; если обновление почистило outbox или сбросило
   seq — реплей пуст, список не восстанавливается.

4. **Version-check уводит bundled-клиент с приложения** — HomeScreen каждые
   5 минут сравнивает version.json; при смене версии делает
   `window.location.href = reloadUrl` (голый адрес сервера!) для bundled
   (`file:` или AlphaConfig.serverUrl). В репо Android-бридж AlphaConfig не
   найден + androidScheme https -> для Android путь должен сводиться к
   безопасному location.reload(); проверить на устройстве, не меняется ли
   URL после обновления сервера.

## Диагностика
- Воспроизвести: обновить сервер при открытом/фоновом приложении; смотреть
  logcat/console: меняется ли document.location; какие коды ответов REST.
- Сверить: живы ли строки sessions в БД после апдейта (должны — обычная
  таблица).

## План исправления
- Повторные попытки boot-загрузки (backoff) либо перезапуск getChats/getMe
  по 'synced' после reconnect.
- Глобальный перехват 401 -> clearSession -> экран входа.
- На Android foreground: после ws.reconnect() дергать getChats/getMe
  (идемпотентно).
- Version-check: авто-reload только для веба (не bundled); для bundled —
  баннер «доступно обновление» вместо навигации.

## Реализация (2026-08-21)
1. **refreshSnapshot** в HomeScreen: getChats + getMe вынесены в функцию;
   вызывается на boot и на каждом 'synced' (конец реплея после любого
   успешного реконнекта) — вход в окне рестарта сервера больше не оставляет
   пустое состояние: как только WS долинковался, REST-снапшот
   восстанавливает список и профиль.
2. **401-перехват** в api/rest.ts: первый же 401 вне /auth/* при наличии
   токена -> clearSession + один location.reload (флаг от повторов) ->
   экран входа вместо «зомби»-оболочки.
3. **Android foreground**: после ws.reconnect() дергается refreshSnapshot.
4. **Version-check**: полностью пропускается для bundled-клиентов
   (file:, AlphaConfig.serverUrl) — навигация на голый адрес сервера
   невозможна; веб как раньше делает location.reload().

Тесты: e2e/session-expiry.spec.ts (deleteSessions через БД -> клик по чату
-> 401 -> авто-разлогин -> экран входа; повторный reload остаётся на входе).
tsc/vite build — ок. Регресс на run/dev.
